# Estructura del código

Mapa de carpetas del backend, el frontend, el cliente de Linux y el código común, qué hace cada una, qué puede importar de qué y cómo añadir un módulo nuevo. Las reglas de dependencia las comprueban dos tests (`backend/tests/test_architecture.py` y `frontend/test/architecture.test.mjs`): si rompes una, el test falla y dice qué import sobra.

## Backend (`backend/app/`)

```
backend/app/
├── main.py              fábrica de la app (create_app / app_factory): monta middleware, routers y docs
├── cli.py               CLI (`python -m app.cli`): list, sync...
├── api/                 capa web (FastAPI)
│   ├── auth.py          sesiones, login, API key en cabecera
│   ├── deps.py          dependencias de FastAPI (require, usuario actual; keys Bearer: `hook_user` = usuario, `hook_device` = dispositivo http, `hook_any` = las dos, todas devuelven `Principal(user, device|None)`)
│   ├── middleware.py    log de depuración de cada petición
│   ├── docs/            OpenAPI y Swagger de la API key (install, models, examples, pairing, steam)
│   └── routers/         un router por área: hook, games, session, profile, devices (API key por dispositivo http, con sesión), config, sync,
│                        versions, orphans (datos sin dispositivo ni juego: `GET /api/orphans`, `POST /api/orphans/relocate` (reubica un juego huérfano en un juego de la config), `POST /api/orphans/trash`, `GET /api/orphans/trash` y `POST /api/orphans/trash/restore`, solo con sesión), scheduler, updates, pairing (vinculación por solicitud y código: la parte pública es el ÚNICO endpoint con escritura sin key ni sesión), deck (descarga PÚBLICA y de solo lectura del zip del plugin: `GET /api/deck/plugin`, `/api/deck/plugin.sha256` y `/api/deck/plugin/info`; sin parámetros, ruta fija `settings.DECK_ZIP`), steam (asociación de `steam_appid` desde la Deck: `POST /api/steam/library` solo `ckd_`, y sugerencias/descartes con sesión) y spa (catch-all, siempre el último)
├── services/            lógica de negocio sin FastAPI
│   ├── context.py       AppContext: objetos compartidos de la app (auth, scheduler, watcher...)
│   └── runs, pairing, deckplugin (lee el zip UNA vez, calcula SHA-256 y versión de `Checkpoint/package.json`; caché por mtime y tamaño; se sirven los mismos bytes que se hashearon), hooks (aviso `opened`, cierre y, para dispositivos http, `fingerprint`, `closed`, `manifest`, subida `files` y `commit`, purga y tope del staging), steam (normalización y coincidencia de nombres, sugerencias en memoria y descartes en `data/state/_steam/dismissed.json`; `purge` en `scheduler.maintenance`), orphans (detección de datos de un origen desconocido o de un juego fuera de la config, con `token` por elemento; mover a la papelera revalidando con la config actual y bajo el lock del juego; listar, restaurar y vaciar lo caducado: `purge_expired` en `scheduler.maintenance`), hookfiles (staging reanudable, `part_lock` por fichero y `stage_lock` del dispositivo durante el commit, tope y lectura por rangos de las subidas/bajadas http), devices, games, status, versions
├── sync/                motor de sincronización
│   ├── engine.py        run_sync, restore_version, resolve_game; `write_winner_to_hub` y `finish_hub_update` (aplicar un ganador al hub, compartido con el commit HTTP)
│   ├── safepath.py      `resolve_inside`: ruta relativa segura dentro de una raíz (sin `..`, ni enlaces simbólicos); obligatoria al leer o escribir con rutas de un dispositivo http
│   ├── decide.py        decisión pura de quién manda y resolución de conflictos
│   ├── fingerprint.py   huella de un directorio o de un manifiesto (`fingerprint_from_manifest`)
│   ├── versions.py      versiones guardadas, `current_state` (estado del hub solo con `stat`, para `current` de `/limit`) y reemplazo casi atómico de directorios
│   ├── baseline.py      huella de cada participante tras la última sync completa (`drop_baseline` quita un origen)
│   ├── cleanup.py       `purge_device_metadata`: al borrar un dispositivo, limpia SOLO sus metadatos (baseline, staging, resoluciones), con el lock del juego; nunca versiones ni hub
│   ├── trash.py         papelera `data/trash/<fecha>/` con `manifest.json` (rutas relativas), caducidad (`settings.TRASH_TTL_DAYS`), mover y restaurar sin pisar ni seguir enlaces
│   ├── resolution.py    conflictos de datos de dispositivos http y su resolución pendiente (`data/resolutions/<juego>.json`)
│   ├── errors.py        SyncAbort
│   ├── locking.py       lock por juego
│   ├── scheduler.py     sincronización automática + tareas de mantenimiento periódicas (`maintenance`: purga del staging)
│   ├── watcher.py       vigilancia del cierre del juego
│   └── transport/       acceso a dispositivos: base (interfaz y utilidades), posix (ssh + rsync),
│                        windows (ssh + tar) y local («Este equipo»); __init__ reexporta lo público
├── config/              modelo (models.py) y almacén (store.py) de config.yaml; `Game.steam_appid` (opcional; entero > 0, único entre juegos) y `Game.steam_appids` (opcional; `{dispositivo: appid}`, claves = dispositivos del juego; `Game.effective_appid(dispositivo)` = el del mapa o, si no, el general; único por dispositivo en `semantic_errors`) los expone `GET /api/games` (con key de dispositivo, solo el efectivo en `steam_appid`)
├── users/               datos por usuario: apikey (key de usuario `ck_` y de dispositivo http `ckd_`, mismo almacén cifrado), avatar, history
└── core/                utilidades base: settings, errors, hosts, bootstrap, redact, runtime, updates
```

### Reglas de dependencia (backend)

Las capas se apilan: `api` → `services` → `sync` / `config` / `users` → `core`. Nunca se importa hacia arriba.

| Capa | Puede importar de | No puede importar de |
|---|---|---|
| `core` | solo de sí misma | ninguna otra capa |
| `sync`, `config`, `users` | `core` y entre ellas | `api`, `services` |
| `services` | `sync`, `config`, `users`, `core` | `api` |
| `api` | todas | (ninguna) |

Excepción documentada: `sync/scheduler` importa `users/history` (registra en el historial de cada usuario el resultado de sus ejecuciones). Está en la lista `ALLOWED` del test; si deja de hacer falta, el test pide borrarla.

Para repartir los imports públicos de un paquete sin romper a quien ya importa de él, el `__init__.py` reexporta (por ejemplo `sync/transport/__init__.py`, o `sync/engine.py` con las funciones que viven en `decide`, `fingerprint`, `versions` y `baseline`). Los tests que sustituyen una función con `monkeypatch` deben apuntar al módulo donde se *usa* (p. ej. `app.sync.engine.get_transport`, `app.sync.transport.base._run`).

### Añadir un módulo al backend

1. Decide la capa por la regla de arriba: ¿habla HTTP? `api`. ¿Orquesta casos de uso sin conocer FastAPI? `services`. ¿Es del motor de sincronización? `sync`. ¿Es del fichero de configuración? `config`. ¿Es dato de un usuario? `users`. ¿Lo usan todas las capas y no depende de ninguna? `core`.
2. Un endpoint nuevo: crea `api/routers/<area>.py` con un `APIRouter`, regístralo en la lista de `main.py` (antes del router `spa`) y pon la lógica en `services/`. Por defecto queda fuera del esquema público de OpenAPI; solo las rutas con el tag `TAG` de `api/docs/install.py` salen en Swagger.
   Autenticación de `/api/hook/*` y `/api/games`: no hay dependencia global; cada endpoint declara la suya según la key que acepta (`deps.hook_user` usuario: `watches`; `deps.hook_device` dispositivo: `fingerprint`, `manifest`, `files`, `commit`, `closed`; `deps.hook_any`: `ping`, `GET /api/games` y `opened`: con `ckd_` es el aviso de apertura de un http (`HookService.opened_device`), con `ck_` el de siempre; `GET /api/games` que con key de dispositivo filtra por sus juegos y añade `path` = `Game.paths[<ese dispositivo>]` o `null`, vía `routers/games.device_path`; con key de usuario no hay `path`). La clase equivocada es el mismo 401 que una inválida y cuenta para `hook_fail`. Un endpoint nuevo debe elegir una; `docs/install.KEY_KINDS` la declara para el Swagger (un único esquema Bearer `bearerAuth` para `ck_` y `ckd_`; la clase aceptada va en la nota «Key aceptada» de cada operación) y `test_apidocs`/`test_device_apikey` fallan si falta o no coincide. Con key de dispositivo, `HookService.scope` fija dispositivo y juego (403 `err.apikey.device_mismatch` si `?device=` no es el de la key; 404 `err.main.game_unknown` si el juego no lo incluye). Las keys de dispositivo viven en `users/apikey` (`devices/<id>.enc`, ligadas al id de dispositivo) y se podan con `services/devices.prune_device_keys` al guardar/restaurar la config y al arrancar.
   Vinculación de dispositivos (`routers/pairing.py` + `services/pairing.py`, docs en `api/docs/pairing.py`): dos routers en `/api/pairing`. `POST /requests` y `GET /requests/{id}` son PÚBLICOS (sin key ni sesión; el único caso: `KEY_KINDS` = `public` y `pairing_secret`, secreto en la cabecera `X-Pairing-Secret`, nunca en la URL) y limitados por IP (`Auth.pair_fails`, `pair_wait/pair_fail/pair_ok`, más los topes y la caducidad de `PairingService`, con el reloj de `Auth`); `GET /pending` y `POST /pending/{id}/accept|reject` exigen sesión (`session`). Las solicitudes viven solo en memoria (`ctx.pairing`, `purge` en `scheduler.maintenance`). Aceptar da de alta el dispositivo por `ConfigStore.save` (mismas validaciones que `PUT /api/config`) y la key `ckd_` se genera al recogerla, no al aceptar. Una ruta pública nueva sin credencial debe justificarse y pasar por los mismos límites.
   Descarga del plugin (`routers/deck.py` + `services/deckplugin.py`): pública sin credencial pero de SOLO LECTURA, justificada porque el zip es el plugin de código abierto del repositorio y la Deck lo baja sin cuenta; la integridad la da la suma SHA-256 (cabecera `X-Checkpoint-Plugin-Sha256`, `.sha256` para `sha256sum -c` e `info`). Ruta fija (`settings.DECK_ZIP`: Docker `/app/deck/Checkpoint.zip`, que construye el Dockerfile; nativo `checkpoint-deck/out/Checkpoint.zip` tras `pnpm run zip`); sin zip, 404 `err.deck.plugin_missing`. Fuera del Swagger de la API key.
   Asociación de Steam (`routers/steam.py` + `services/steam.py`, docs en `api/docs/steam.py`): `device` (`POST /api/steam/library`, `POST /api/steam/games` y `PUT /api/steam/games/{game}/enabled`, `deps.hook_device`, `KEY_KINDS` = `device`) solo toca juegos activos que tienen ese dispositivo y solo escribe `steam_appid` con coincidencia exacta y única de nombre normalizado en un juego sin appid y con el appid libre, o `steam_appids[dispositivo]` (nunca el general) si el juego ya tiene un general distinto y el nombre es único entre los juegos activos del dispositivo (`plan_matches`, pura; `Plan.associate` / `Plan.associate_dev`); lo dudoso (parecido con `SIMILARITY` = 0,85, o ambiguo) son sugerencias en memoria; `session` (`/api/steam/suggestions*`, `/api/steam/dismissed*`, `KEY_KINDS` = `session`). Escribe config por `ConfigStore.save` con la versión de la misma lectura y reintentos. Nunca pisa un appid existente. `POST /api/steam/games` (`SteamService.create_game`) crea un juego con SOLO el dispositivo de la key, activo, con `steam_appid`, nombre y ruta que da la Deck: el id lo genera el hub (`slug` del nombre, con el appid detrás si colisiona y `steam-<appid>` sin slug), valida con `validate_config` (las mismas reglas que `PUT /api/config`: nombre y ruta válidos, nombre y appid únicos; un fallo es `422 err.steam.game_invalid` con solo `field` y `reason`, sin datos de otros juegos), la plataforma sale del dispositivo. Si ya existe UN juego con ese nombre normalizado (`normalize`, la de `plan_matches`; `SteamService._twins`), `_join` le AÑADE el dispositivo (`devices` + `paths[dispositivo]` validados con `validate_config`, misma versión y reintentos que la creación; pone `steam_appid` si faltaba; si tenía otro general, escribe `steam_appids[dispositivo]` y no toca el general) y responde `{id, name, appid, path, joined, devices, enabled}`; condiciones: hueco (<2 dispositivos), dispositivo fuera, appid no usado por otro juego (hub entero si va al general; efectivo en ese dispositivo si va a `steam_appids`); un juego desactivado se une y sigue desactivado; dispositivo ya dentro con el mismo appid = `joined: false` sin escribir; el resto es `422 err.steam.game_invalid` (`field: name`, `reason`: `err.steam.no_free_slot`, `err.steam.appid_in_use` o `err.config.name_duplicate` si es ambiguo o el dispositivo ya estaba con otro appid). La key solo se añade a sí misma. `PUT /api/steam/games/{game}/enabled` (`SteamService.set_enabled`) pone el campo `enabled` del juego: es de TODO el hub (un juego desactivado no se sincroniza por ninguna vía en ningún dispositivo), solo para juegos que tienen ese dispositivo (otro caso, el mismo `404 err.steam.game_unknown`). `PUT /api/steam/games/{game}/path` (`SteamService.change_path`, cuerpo exacto `{path}`) cambia SOLO `paths[dispositivo]` de uno de sus juegos: valida con `validate_config` (`422 err.steam.game_invalid`, campo `path`), si es la misma ruta responde 200 sin escribir; si hay ejecución en curso (`game_busy`, que `AppContext` inyecta en `SteamService`) o el lock del juego está tomado, `409 err.main.run_in_progress`; bajo ese lock guarda la config (mismos reintentos que `set_enabled`) y después `drop_baseline` y `resolution.clear` (conflicto y resolución) de ESE dispositivo (mismo patrón que `sync/cleanup.py`), sin tocar otros dispositivos, el hub ni el estado del juego; vale con el juego desactivado. Cuerpos de máx. 8192 bytes con forma exacta (`422 err.steam.game_body_invalid`).
   Los dispositivos `http: true` (`Device.http`) no tienen transporte: `get_transport` lanza `err.transport.push_only` y quedan fuera de `_do_sync`, del scheduler, de `opened` y de la vigilancia (`config.models.classic_devices` lista los que el hub sí contacta; la UI usa el mismo criterio en `components/config/draft.js`: `isHttpOnly` oculta «Sincronizar» y «Simulación» en Sincronizar). Los atiende la API de `routers/hook.py` con `services/hooks.py` (`fingerprint`: no toca ficheros ni historial; escribe la línea base con `none`/`same` y el registro del conflicto con `conflict` (`sync/resolution.py`, que `PUT /resolution` convierte en resolución pendiente y `fingerprint`/`commit` honran si las huellas coinciden), siempre bajo el lock del juego; `closed`: limpia el «jugando» y registra el cierre en el historial, sin sync; `opened_device` (key `ckd_` en `opened`): sin sync ni vigilancia, marca «jugando» en `HookService._playing` (en memoria, caduca a `settings.HOOK_PLAYING_TTL`) y anota `hook_opened`; ambos aceptan el cuerpo opcional `{result: {state, code?}}` (`parse_sync_result`: lista cerrada, 1 KiB, `err.hook.result_invalid`), que queda en el historial como `code` `hook.sync.<estado>`; `GET /api/watches` expone `playing` y `results` (`active_playing`, `last_sync_results`; la UI pinta `playing` con `components/watch/PlayingBars.jsx`, que reutiliza `WatchBar` como la vigilancia clásica; `results` alimenta el Registro y la tarjeta de un juego solo http en Sincronizar: `lastHttpResult` elige el último, `httpRunStatus` lo adapta a `LastRun` (bloque «Última sync») y `httpBadge` deriva la insignia del título, en vez del estado antiguo del hub, en `components/watch/watch.js`); subida: `PUT files` escribe solo en `data/staging/<juego>/<dispositivo>/` SIN el lock del juego (solo guarda `game_busy` y un lock por fichero, `hookfiles.part_lock`) y únicamente `commit` toca `data/hub/<juego>`, con el lock del juego, comprobando `expect`; el staging se purga por antigüedad (`CHECKPOINT_HOOK_STAGING_TTL_H`, al arrancar y cada hora vía `Scheduler.maintenance`, sin tocar juegos con lock o run) y tiene tope por juego (`CHECKPOINT_HOOK_STAGING_MAX_MB`, `err.hook.staging_full`); `fingerprint?manifest=1` devuelve `hub_manifest` de la misma lectura (`fingerprint_with_manifest`); bajada: `manifest`, `GET files` con `Range`; la línea base del dispositivo la fija después un `fingerprint` igual). `/api/devices/test` con un `http` responde `err.transport.push_only` sin intentar SSH. El manifiesto solo rechaza rutas que escapan (`..`, absolutas, NUL, vacías, repetidas): no usa `PATH_CHARS_RE`, que queda para rutas de dispositivo. Como esas reglas son relajadas, toda ruta que se lea o escriba en disco (staging o hub) debe pasar por `sync/safepath.resolve_inside`.
3. Un transporte nuevo: módulo en `sync/transport/` que implemente `Transport` (de `base.py`) y exporta en `__init__.py`; engánchalo en `get_transport`.
4. Textos para el usuario: el backend no traduce; devuelve códigos `err.<módulo>.<causa>` con `params` y la traducción va en `frontend/src/locales/*.json`.
5. Ejecuta `pytest`: `test_architecture.py` confirma que no has roto las reglas.

`styles/main.scss` solo ordena los `@use`; los parciales de cada componente viven junto a él (`components/ui/`, `components/config/`, `components/autosync/`, `components/profile/`). El orden de los `@use` en `main.scss` importa (cascada): no lo reordenes sin comprobar el CSS resultante. `_components.scss` queda en `styles/`: mezcla reglas globales de varias pantallas (tarjetas, rejilla, modal, conflictos).

Los imports entre carpetas usan el alias `#src/` (`package.json` → `imports`: `#src/lib/api.js`); dentro de una misma carpeta, rutas relativas (`./Button.jsx`). Se usa `#src/` y no `#/` porque Node no admite subpaths que empiecen por `#/`. Funciona igual en Vite, en esbuild (tests) y en Node.

### Reglas de dependencia (frontend)

| Carpeta | Puede importar de | No puede importar de |
|---|---|---|
| `lib` | solo de `lib` (y recursos) | React, `hooks`, `components`, `pages` |
| `hooks` | `lib`, `hooks` | `components`, `pages` |
| `components/ui` | `lib`, `hooks`, `ui` | zonas, `pages` |
| `components/<zona>` | `lib`, `hooks`, `ui` y su propia zona | otra zona, `pages` |
| `pages`, `App.jsx` | todo | (ninguna) |

`assets/`, `locales/` y `styles/` son recursos: los puede importar cualquiera. Si dos zonas comparten algo, súbelo a `ui` (si es de interfaz) o a `lib` (si es lógica): por eso `updates.js` y `apikey.js` viven en `lib/` (los usan varias zonas). Algunos módulos de `lib` usan el navegador (`clipboard`, `pwa`, `launchers`), pero ninguno importa React.

Todas las llamadas a la API pasan por `lib/api/<recurso>.js` (`session`, `config`, `sync`, `versions`, `updates`, `profile`); los componentes no llaman a `api()` directamente. Dos componentes (`ApiKeySection`, `LauncherBlock`) reciben el cliente por prop `api` para poder sustituirlo en los tests.

`components/ui/index.js` reexporta los componentes de uso común; `Icon`, `Modal`, `Field`, `EmptyState` y `AppIcon` se importan directamente desde su fichero.

### Añadir un módulo al frontend

1. Componente genérico y reutilizable (varios usos, sin lógica de negocio): `components/ui/<Nombre>.jsx`, su parcial `_<nombre>.scss` al lado, y la línea en `components/ui/index.js` y en `components/ui/_index.scss`. Con tres o más usos de un mismo patrón, conviértelo en componente.
2. Componente propio de una funcionalidad: en la zona que corresponda (`components/<zona>/`), con sus ayudas puras (`.js`) al lado. Zona nueva: carpeta nueva con su parcial SCSS y su `@use` en `styles/main.scss` en el sitio correcto de la cascada.
3. Una llamada nueva a la API: función en `lib/api/<recurso>.js`; el componente importa la función, no `api()`.
4. Lógica compartida sin React: `lib/`. Estado compartido con React: `hooks/`.
5. Textos: claves en `locales/es.json` y `en.json` con las mismas claves (`locales.test.mjs` lo comprueba). Tamaños de texto con los tokens `$fs-*` de `styles/_variables.scss`.
6. Tests: en `frontend/test/` en el mismo sitio que el fichero (`test/components/<zona>/...`), con `test/helpers/bundle.mjs` para renderizar componentes y `test/helpers/locales.mjs` para los catálogos. Ejecuta `npm test`: `architecture.test.mjs` comprueba las reglas de dependencia.

## Plugin de Steam Deck (`checkpoint-deck/`)

Plugin de Decky Loader, aparte del backend y del frontend: no lo importa ni lo ejecuta el hub, y los linters y tests del hub no lo recorren. Se empaqueta a zip con `checkpoint-deck/scripts/package.sh` (el zip no se commitea). El Dockerfile lo construye en la etapa `deck` (antes, la etapa `savemanifest` baja el manifiesto de Ludusavi de un commit fijo, `LUDUSAVI_MANIFEST_COMMIT`, y ejecuta `gen_save_manifest.py`; el JSON va al zip por `SAVE_MANIFEST` y el build falla si la descarga o el generador fallan; `--build-arg SKIP_SAVE_MANIFEST=1` lo omite a propósito) y lo copia a `/app/deck/Checkpoint.zip`; el hub lo sirve en `/api/deck/plugin` y la web lo ofrece en Configuración > Lanzadores, abajo del todo (no existe aún una página «Herramientas»). Versiones y actualizaciones (decisión cerrada): el plugin tiene versión propia semver (`checkpoint-deck/package.json`, arranca en `1.0.0`; el hub la lee del zip) y declara `checkpointProtocol` (entero). La compatibilidad va por protocolo, no por versión: `backend/app/core/protocol.py` fija `PROTOCOL` y `MIN_PLUGIN_PROTOCOL` (ambos 1), `GET /api/hook/ping` los devuelve como `protocol` y `min_plugin_protocol` (campos nuevos: los clientes viejos los ignoran) y `GET /api/deck/plugin/info` añade `protocol`. «Probar conexión» avisa si el protocolo del plugin es menor que `min_plugin_protocol` (plugin bloqueado: no sincroniza hasta actualizar), si el hub no anuncia protocolo (hub viejo: aviso sin bloquear) o si el plugin no puede leer el suyo. Actualizar es SOLO por URL de Decky (decisión cerrada; el plugin no descarga ni instala nada ni escribe en su carpeta): «Buscar actualizaciones» consulta `/api/deck/plugin/info` (público, sin clave `ckd_`), solo ofrece una versión estrictamente mayor (semver propio con solo la biblioteca estándar; una pre-release como `1.0.0-rc.1` es MENOR que su release `1.0.0`) y el panel da los pasos: Ajustes de Decky > Desarrollador > «Instalar plugin desde URL», pegar `<hub>/api/deck/plugin` y reiniciar Decky si no se recarga solo. Probado en una Deck real: la instalación por URL de Decky, el selector de carpetas y el panel. Sin comprobar: el comportamiento exacto en otras versiones de Decky.

## Instalador de Windows (`packaging/windows/`)

Empaqueta el hub en modo nativo para Windows. No es parte de la imagen de Docker (`.dockerignore` lo excluye) ni importa nada del frontend.

- `checkpoint.spec`: PyInstaller onedir sin consola. Mete `frontend/dist` como `static/`, `checkpoint-deck/out/Checkpoint.zip` como `deck/` y `VERSION` junto a `app/` (el mismo diseño que `/app` en Docker; con el hub congelado `settings.DECK_ZIP` busca `deck/`). Falla si falta alguno.
- `launcher.py`: punto de entrada. Lee `%APPDATA%\checkpoint\.env`, rechaza el modo sin login con un host no local, redirige la salida a `logs/checkpoint.log`, lanza la bandeja y, con `--open`, abre el navegador.
- `tray.py`: icono de bandeja (pystray + Pillow) con «Abrir» y «Detener»; si no puede arrancar, el hub arranca igual.
- `installer.iss`: Inno Setup (por usuario, es/en, asistente de credenciales, desinstalador que pregunta si borrar los datos). Parámetros silenciosos `/NOLOGIN=1`, `/CPUSER`, `/CPPASSWORD`.
- `build.ps1` y `smoke.ps1`: construcción completa y smoke test (los usan el job `windows-installer` de `ci.yml` y el job `windows` de `release.yml`); `requirements.txt`: PyInstaller, pystray y Pillow.
- Backend: `services/autostart.py` (Tarea Programada, `GET`/`PUT /api/autostart`) y `services/selfupdate.py` (actualización con un clic, `POST`/`GET /api/updates/install`; solo con el hub congelado en Windows). El asset de la Release es `Checkpoint-Setup-<versión>.exe` más su `.sha256`; `core/updates.py` solo lo ofrece si están los dos.

## Paquete de Linux (`packaging/linux/`)

Empaqueta el hub en modo nativo para Linux (servicio de usuario de systemd, sin root). No es parte de la imagen de Docker ni cambia el código del hub.

- `build.sh`: construye `dist/checkpoint-<versión>-linux.tar.gz` y su `.sha256` (carpeta raíz `checkpoint-<versión>/` con `install.sh`, `VERSION`, `backend/{app,requirements.txt,static}` y `checkpoint-deck/out/Checkpoint.zip`). Reproducible; con `--tag` comprueba `VERSION`.
- `install.sh`: instala (`--no-login`, `--user`/`--password-file`, `--host`, `--port`, `--no-start`, `--dry-run`, `--enable-linger`), actualiza (`--upgrade`, con vuelta a la versión anterior si el reinicio falla) y desinstala (`--uninstall`, `--purge`). Código en `~/.local/share/checkpoint-app/<versión>/` con el enlace `current`, entorno en `~/.config/checkpoint/checkpoint.env` y unidad `~/.config/systemd/user/checkpoint.service`. Variables: [`configuration.md`](configuration.md#instalación-nativa-en-linux-installsh).
- `smoke.sh`: smoke test sin systemd real (lo usan el job `linux-package` de `ci.yml` y el job `linux` de `release.yml`).
- Backend: `services/selfupdate.py` (actualización con un clic: descarga, verifica el SHA-256, extrae con seguridad y lanza `install.sh --upgrade` desacoplado; solo con una instalación hecha por `install.sh`). Publica `espera_reinicio` (s) en `GET /api/updates`: 120 en Windows, 300 en Linux.

## Cliente de Linux (`checkpoint-client/`)

Paquete Python `checkpoint_client` (CLI `checkpoint-client`, Python 3.12, dependencias `psutil` y `keyring`) que sincroniza sin SSH con el hub, como el plugin de la Deck pero para Linux de escritorio. Es independiente del hub (no lo importa ni lo ejecuta; el Dockerfile no lo copia y `.dockerignore` lo excluye) y tiene versión propia semver en su `pyproject.toml`, que no depende del tag del hub. Su `README.md` explica el uso; aquí solo el empaquetado y la CI.

- **Wheel:** `python -m build --wheel` desde `checkpoint-client/` (el sdist no es posible: `package-dir` toma `checkpoint_core` de `../checkpoint-core/src`). El job `client` de `release.yml` lo construye en cada tag, comprueba que lleva `checkpoint_client/` y `checkpoint_core/` y ningún `secrets.py`, y lo sube a la Release del tag (`gh release upload --clobber`, con `contents: write` solo en ese job). `checkpoint-client check-update` lee la versión nueva del nombre de ese asset en la última Release estable.
- **CI (`ci.yml`):** job `client` (Python 3.12: instalación editable con extras `dev`, `ruff check`, `ruff format --check`, `pytest`; las pruebas de integración con el hub real se omiten porque el job no instala las dependencias del backend) y job `core` (`checkpoint-core/`, mismos pasos en Python 3.8 y 3.12).
- **Auditoría y dependencias:** `audit.yml` audita las dependencias de ejecución de cada `pyproject.toml` que no tenga `requirements.txt` al lado (hoy, `psutil` y `keyring` del cliente) con `pip-audit`; `dependabot.yml` vigila `/checkpoint-client` y `/checkpoint-core` con `pip`.

## Código común del plugin y del cliente (`checkpoint-core/`)

Paquete Python `checkpoint_core` con lo que debe ser idéntico en el plugin de la Deck y en el cliente de Linux (`checkpoint-client/`), para no copiarlo: solo código PURO (sin asyncio, ni Decky, ni Steam, ni red) y solo biblioteca estándar. Compatible con Python 3.8 (Decky corre en su propio Python: no uses sintaxis más nueva que la del plugin); `ruff` con `target-version = "py38"`.

```
│   ├── names.py       `normalize_device_name`, `DeviceNameError`, `NAME_MAX` (reglas de `name_error` del hub)
│   ├── redaction.py   `redact` y `describe_error`: claves `ck_`/`ckd_` y secretos; cada cliente suma sus patrones con `extra` (el plugin, los steamid)
│   ├── protocol.py    `KEY_PREFIX`, `parse_protocol` y `compat` (`ok`, `hub_old`, `plugin_unknown`, `plugin_outdated`)
│   └── version.py     `parse_semver`, `compare` e `is_newer` (semver; una pre-release es menor que su release)
└── tests/             pytest propio (las reglas, sin hub)
```

La fuente es única: ni `checkpoint-deck/` ni `checkpoint-client/` guardan una copia. Cómo llega a cada consumidor:
- **Plugin de la Deck:** `checkpoint-deck/scripts/package.sh` copia `../checkpoint-core/src/checkpoint_core/*.py` a `Checkpoint/py_modules/checkpoint_core/` dentro del zip (Decky pone `py_modules/` en `sys.path`; el zip sigue siendo autocontenido y solo stdlib). La etapa `deck` del Dockerfile hace `COPY checkpoint-core/src /checkpoint-core/src` para que `../checkpoint-core` exista desde `/deck`. Las pruebas del plugin lo importan por `tests/conftest.py` (añade la ruta del core).
- **Cliente de Linux:** `checkpoint-client/pyproject.toml` empaqueta `checkpoint_core` desde `../checkpoint-core/src` (`package-dir`): el wheel lo lleva dentro y no hay dependencia aparte. Construye con `python -m build --wheel` (el sdist por defecto no es posible: `package-dir` apunta fuera de la carpeta del cliente). `pip install .` y `pip install -e .` desde `checkpoint-client/` también funcionan.

Qué NO se unificó (sigue en cada lado a propósito): los motores de sincronización (asyncio en el plugin, síncrono en el cliente), todo lo de Steam, la vinculación y el HTTP (`checkpoint_hub`/`hub` y `checkpoint_client`/`hubclient`, que usan la red), los ajustes en disco (`save_settings` difiere: el cliente fuerza 0700 en su carpeta, el plugin no toca la de Decky) y la lectura de la versión propia del plugin (`checkpoint_version`: `plugin_dir` y `read_version`, que leen su `package.json`; el semver en sí, `parse_semver`/`compare`/`is_newer`, sí está en el core).

Regla de pruebas: cada carpeta con código tiene su propio pytest y sus propias pruebas (`backend/`, `checkpoint-deck/`, `checkpoint-client/`, `checkpoint-core/`), y una prueba vive donde vive el código que prueba. Una regla del core se prueba en `checkpoint-core/tests/`, no otra vez en el plugin ni en el cliente; allí solo quedan las pruebas de integración (p. ej. la equivalencia del manifiesto con el `fingerprint` del hub real).
